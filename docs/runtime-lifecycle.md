# Runtime lifecycle ownership

Status: Docker teardown, event deadlines, repeatable deletion, application resource ownership, and explicit store/Docker/instance initialization passed user-run tests and quality checks. Shutdown reservation handling below awaits verification.

Closing the Docker backend releases its event subscription, event listener, and Docker client. It must not stop or remove customer containers. Explicit instance deletion remains the operation that removes a workload. Closing is repeat-safe, later calls are rejected, and client cleanup is attempted even when listener cleanup fails.

The event listener rejects new waiters after close and completes outstanding waiters when their stream generation fails. Failed/cancelled waits release their registrations. Backend command failures also release their event waiters so retries are not blocked by abandoned registrations. Stream errors or unexpected completion trigger reconnect attempts with bounded exponential backoff (100 ms to 5 seconds); receiving an event resets the backoff. Events and failures from an obsolete connection generation are ignored. Waiters active at a stream failure fail promptly and callers must retry after reconnection.

Each event wait has a 60-second deadline beginning at registration, before command submission. Java's CompletableFuture timeout support removes completed waits' timers without a separate application-owned scheduler. Timeout, cancellation, stream termination, command failure, and executor rejection release the registration. Cleanup only removes that specific future, so an older wait cannot remove a later retry. After the Docker command finishes, start/stop inspects the container regardless of whether its event arrived. A confirmed desired state counts as success; a different observed state is recorded as that actual stable state by the instance service; inspection failure preserves the transitional reservation for recovery. Lifecycle events cause a fresh inspect before changing cached backend status, so a late event cannot overwrite newer observed state.

Start/stop operations retain command-completion gating: an expired event wait does not finish the operation while its Docker command remains in flight. Queued commands check expiry/cancellation before execution and are skipped if already abandoned. Cancelling the returned future releases its event wait. Neither cancellation nor a deadline interrupts an already-running Docker command; the SDK transport timeouts still govern that request, and a timed-out request can have uncertain late effects at Docker. This checkpoint does not claim a hard end-to-end deadline or safe distributed fencing of late commands.

Docker deletion is repeatable: an absent container mapping or a Docker not-found response counts as success. Other Docker failures propagate and preserve the mapping for retry. This supports retrying an instance deletion when its container removal succeeded but its subsequent metadata deletion failed.

`Main` now installs one shutdown hook for `ApplicationRuntime`. Every component registers its resource owner before constructing its web service or resolving handlers. Failed construction/startup closes the failed component's resources and all services already started. Normal shutdown stops all HTTP services before closing component resources. Web service start/close is repeat-safe and cannot restart after close; callers using `create()` directly still own the returned Javalin instance.

Instance reconciliation during startup has a 120-second default overall deadline, configurable with the `minicloud.instance.startup-deadline-seconds` JVM property. Recovery is serialized and checks the deadline before starting each row. Expiry fails initialization so `ApplicationRuntime` closes partial resources before HTTP starts. In-flight Docker commands are not interrupted; their transitional metadata is retained and callbacks cannot update it after the instance service closes. This deadline covers instance reconciliation only; store initialization and Docker container discovery occur earlier and use their configured request timeouts.

`InstanceServiceImpl.close()` rejects new API work, unsubscribes health events, and drains tracked lifecycle completions for up to five seconds by default. `minicloud.instance.shutdown-drain-seconds` configures this wait; zero skips it. Runtime cleanup then closes the Docker backend and drains the shared worker executor. If the service drain expires, transition reservations remain for recovery and late callbacks cannot update metadata. This bounds the service drain but does not impose a hard deadline on Docker/client close, HTTP close, or the full process teardown.

Each Dagger component shares one DynamoDB client and one virtual-thread executor. Providers register resources immediately. Docker client/listener remain individually owned if backend construction fails; once construction succeeds, their ownership transfers to the backend that already closes both. Component shutdown closes backend resources first, drains its executor for up to five seconds, requests interruption if needed, waits up to five more seconds, then closes data clients and remaining mDNS responders. Cleanup failures are logged and do not skip other resources. mDNS registration failure closes its partial responder; duplicate registration does not create another one.

`InstanceServiceImpl` construction no longer subscribes to events or starts reconciliation. The runtime registers the managed singleton before calling its explicit, repeat-safe `initialize()` method. Initialization subscribes to health events and waits for reconciliation before HTTP construction/start. Store scan, status lookup, deletion recovery, or reservation failures that escape reconciliation abort startup and trigger runtime cleanup. Individual start/stop recovery failures still use the existing `MISSING` state and logging policy. Initialization failure removes its subscription and prevents retry on the same object. Shutdown unsubscribes the exact registered consumer before backend teardown. Direct service users and test fixtures must explicitly initialize when they need reconciliation or health events.

Docker backend and event-listener constructors now only retain dependencies and validate configuration. After runtime ownership is registered, `Main` calls `ComputeBackend.initialize()` before instance reconciliation. Docker initialization starts its listener, waits for container discovery, and subscribes to container events once. Repeated initialization is a no-op; initialization after close fails. Backend operations and event waits reject use before initialization. A startup exception closes partially opened resources without deleting workloads and makes that backend unusable. Event-stream submission is asynchronous in the Docker SDK: initialization does not promise the stream cannot subsequently fail; terminal stream failures still fail pending/future event waits.

DynamoDB store constructors now build table mappings without remote calls. A component-scoped `StoreInitializer` initializes the same concrete user, account, credential, session, and policy stores used through service interfaces before HTTP starts. The instance component also initializes its instance store before Docker and instance reconciliation. Table initialization failure propagates through application startup and closes the component's resources. Directly constructed stores must explicitly call `initialize()` before storage operations. A scoped initializer does not repeat successful initialization; a failed attempt may be retried explicitly. The old session store test-only constructor issued a fire-and-forget TTL update; that unused side effect was removed rather than preserved in a constructor.

On shutdown, `InstanceServiceImpl.close()` unsubscribes from health events and rejects new API calls. Backend event waits may then fail as the Docker listener closes. Completion callbacks that run after the instance service closes leave `STARTING` or `STOPPING` unchanged instead of marking the instance `MISSING`; startup reconciliation can inspect the backend and finish the reserved transition. A health read that started before close also checks the closed flag before writing. This is a best-effort process shutdown rule, not distributed fencing: a completion racing with close can still commit its state before observing the closed flag, and requests already executing during HTTP teardown may finish.

The executor wait is bounded; this is not a hard bound on the entire shutdown path. HTTP, SDK, stream callbacks, or mDNS close calls may still block. Closing the backend before draining workers can fail queued/in-flight operations, including writing `MISSING` from completion callbacks; DynamoDB remains open for those callbacks until the worker drain finishes. Customer containers are preserved. Store, Docker, and instance initialization wait synchronously and may delay shutdown coordination. Cancellable startup with a deadline, preserving uncertain operation intent during shutdown, and a global teardown deadline remain follow-up work.

Deadline tests advance futures manually through a package-private deadline seam; they do not sleep or wait for a real 60-second timer. Runtime tests cover HTTP-before-dependency ordering, partial-start rollback, ownership transfer, bounded executor shutdown/interruption, and repeated close. Web/mDNS tests use mocks without opening ports or multicast responders. Run the full suite:
